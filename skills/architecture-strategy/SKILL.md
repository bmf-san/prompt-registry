# アーキテクチャ戦略

アーキテクチャの意思決定を「戦略（Why & What）／戦術・設計（How）」の複数レイヤーで支援するための評価基準・手順・レビュー観点の集約。手段（マイクロサービス化など）が目的化していないかを常に問い、課題分析→方針→施策の筋の通った意思決定を導く。

## いつ使うか

- アーキテクチャ戦略を策定・評価するとき（良い戦略か悪い戦略かを見分けたいとき）
- 技術選定・設計判断で、制約とトレードオフを明示して後から再評価できる記録を残したいとき → [reference/technology-selection.md](reference/technology-selection.md)
- システム設計を進める、またはレビューするとき
- 戦略のレビューチェックリストが必要なとき → [reference/strategy-review.md](reference/strategy-review.md)

## 戦略・戦術・設計の3層

アーキテクチャの意思決定は3層に分かれる。どの層の話をしているのかを常に意識する。

| 層 | 問い | 内容 | 詳細 |
|---|---|---|---|
| **戦略（Strategy）** | Why & What | なぜその方針が必要か（目的・動機）、何を達成するか（ゴール） | 本 SKILL の評価基準 ＋ [reference/strategy-playbook.md](reference/strategy-playbook.md) |
| **戦術（Tactics）** | How(大枠) & When/Where/Who | どう実現するか（施策の大枠）、いつ・どこで・誰が実行するか | [reference/system-design-playbook.md](reference/system-design-playbook.md) |
| **設計（Design）** | How(詳細) | 具体的な技術選定・インターフェース設計・実装方針 | 同上 |

**重要な判断基準**: 「手段が前提になっていないか？」を常に問う。「マイクロサービス化する」は戦術・設計であり、戦略ではない。戦略では「なぜマイクロサービス化が必要か」という目的を明確にする。

## 良い戦略・悪い戦略の見分け方

### 良い戦略の3要素

良い戦略は必ず以下の3要素を含む（課題分析→方針→施策の順で構成する）:

1. **課題分析（Diagnosis）**: 現状の問題を明確にし、根本原因と表面症状を区別する。複数あれば優先順位をつける。
2. **基本方針（Guiding Policy）**: 問題へのアプローチ方向を示し、Why（なぜその方針か）を明確にし、トレードオフを明示する。
3. **施策の方向性（Coherent Actions）**: 方針を実現する具体的アクションの大枠を、優先順位と段階的計画とともに定義する。

### 悪い戦略の3つの特徴

1. **抽象性が高い（スローガンだけ）**: 「クラウドネイティブなシステムを構築する」など、何をすべきかが見えない。
2. **本質回避（表面的な対処）**: 「パフォーマンスが悪い」→「サーバーを増強する」など、根本原因を分析していない一時しのぎ。
3. **目標と戦略の混同**: 「デリバリー速度を2倍にする」は目標であり、達成への道筋（戦略）がない。

### Before / After の例

**Before（悪い戦略）**:

```
【戦略】マイクロサービス化を推進する
【理由】スケーラビリティと保守性を向上させるため
【施策】フロントとバックを分離 / サービスごとにチーム編成
```

問題点: 課題分析が不足（なぜ必要か不明）、手段が目的化、現状の何がどう解決されるのか不明。

**After（良い戦略）**:

```
【課題分析】
現状: モノリス構成によりデプロイが相互依存し、リリース速度が低下
- 問題: 一部の変更で全体をデプロイする必要があり、チーム間調整が頻発
- 影響: 機能リリースまで平均2週間、市場投入速度が遅い
- 根本原因: すべての機能が単一アプリケーションに含まれている

【基本方針】
Why: チーム自律性を高め、機能ごとに独立してリリースできるようにする
What: 機能ドメインごとに境界を設け、独立したデプロイを可能にする

【施策の方向性】
1. 機能ドメインの分割基準を策定（ビジネスケイパビリティ単位）
2. 段階的な移行計画（ユーザー管理→注文管理→...の順）
3. 各ドメインのインターフェースを明確化
```

### よくある失敗パターン

1. **手段から入る**: ✗「マイクロサービス化する」 → ◯「なぜ必要か」から始める
2. **課題分析が浅い**: ✗「パフォーマンスが悪い」で終わり → ◯ どこがボトルネックで、ビジネスへの影響は？
3. **施策が抽象的**: ✗「技術的負債を削減する」 → ◯ どの負債を、どの順で、どう削減するか
4. **トレードオフを明示しない**: ✗「スピードと品質を両立する」 → ◯ 現フェーズはスピード優先、品質は〇〇で担保

## 制約とトレードオフを明示する

技術選定や設計判断は、常に限られた条件のもとで複数の選択肢から最適なものを選ぶ行為。どのような前提や制限のもとで判断したかを明文化しないと、後から「なぜこの選択がされたのか」を理解できない。

### 明示することのメリット

1. **意思決定の前提を明示できる**: その時点の状況・制約・評価軸に基づく判断の合理性を、後から説明可能にする。
2. **将来の判断材料になる**: 組織・技術・要求は変化する。過去のトレードオフの記録があれば「いま別の選択肢を取るべきか」を再判断しやすい。
3. **技術的負債の認識と対話ができる**: どこに制限をかけ、どこに妥協したかを共有することで、負債を「意図的な選択」として明文化し、返済計画を見える化する。
4. **チーム内の合意形成・教育に役立つ**: 「なぜこの技術が採用されているのか」の説明コストが下がり、記録を作る過程で認識を擦り合わせられる。

### 記録すべき観点

| 観点 | 説明 | 例 |
|------|------|-----|
| **制約** | 技術的制限・組織的事情・外部要件など | ツール選定の制限、スキルの有無、導入期限 |
| **トレードオフ** | 他の選択肢を採らなかった理由、何を優先し何を諦めたか | 柔軟性よりも運用の単純さを選ぶ |
| **副作用** | 意図しなかったが生じうる影響 | 学習コストの増加、実行時性能への影響 |

制約とトレードオフを明示することは、単なる設計ドキュメントの作成にとどまらず、**組織の技術的意思決定を持続的に進化させるための基盤**である。

### 評価のための問い

- この意思決定において、どのような制約が存在していたか？
- 採用しなかった選択肢は何か？それを選ばなかった理由は何か？
- 将来この判断を見直す必要が生じるとすれば、どのような変化が起きたときか？
- この決定によって生じる副作用や技術的負債は何か？
- チームメンバーは、この意思決定の背景を説明なしに理解できるか？
