# システム設計プレイブック

システムレベル（技術スタック選定・インフラ構成・システム全体の構造）を、保守性・拡張性・スケーラビリティ高く設計するための手順。設計方針をユーザーと合意してから詳細化する。

## 1. 設計準備

設計依頼を受けたら、案を出す前にまず要件・制約を把握する。

### 1.1 要件と制約の理解

要件（何を達成したいか）と制約（守るべき枠）を切り分け、非機能要件を洗い出す。非機能要件は技術選定を縛る制約として振る舞うため、設計初期に列挙する。詳しくは `requirements-engineering` skill を参照する。

### 1.2 現状の把握

既存システムのアーキテクチャ・コードベース、技術的負債、他システムとの依存関係を理解する。

## 2. 設計

### 2.1 設計方針の提案（合意を得てから詳細化）

実装の前に必ず設計方針を提案し、合意を得る。方針には以下を含める:

```
【設計方針】
1. アーキテクチャパターン: 採用するパターンと選択理由
2. 技術スタック: 使用する技術・FW と選択理由（要件・スキル・将来性）
3. 主要コンポーネント: 構成要素と各責務
4. データ設計: DB 選択（RDBMS/NoSQL）とデータモデル概要
5. 非機能要件への対応: スケーラビリティ戦略・可用性確保・セキュリティ対策
【代替案との比較】他の選択肢との比較
【トレードオフ】この設計の利点と欠点
```

### 2.2 設計の詳細化

合意後、アーキテクチャ図（全体構成・コンポーネント間の関係・データフロー）、インターフェース設計（API・コンポーネント間 IF）、データモデル設計（エンティティ・リレーション・スキーマ）、非機能要件の具体化（スケーリング戦略・障害対策・セキュリティ実装）を詰める。

### 2.3 設計品質の確保

非機能要件は ISO/IEC 25010 の8品質特性で評価する: **機能適合性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・移植性**。

システムレベルで特に重視する追加観点:

- **Scalability**: 水平・垂直スケーリング戦略、負荷分散、キャッシング
- **Operability**: デプロイ容易性、構造化ログ設計、監視・メトリクス
- **Cost Efficiency**: インフラ・ライセンス・運用コストの最適化
- **Compliance**: 個人情報保護法・GDPR 等の法的要件、業界標準

すべての観点を常に満たす必要はない。ビジネス要件と制約に応じて優先順位をつけ、トレードオフを明示する。

## やってはいけないこと

- 合意なしに設計方針を詳細化しない
- トレードオフを明示せずに技術選定を断言しない
- チームのスキルや制約を無視した実現不可能な設計を提案しない
- 設計の良い面だけを強調して欠点・リスクを隠さない
- 実現不可能な「理想的な設計」を実用的な選択肢として押し付けない
- 短期的な実装の容易さだけで設計を評価しない

## 対応する設計タスクの例

新規システムのインフラ設計、既存システムのリアーキテクト、マイクロサービス vs モノリス判断、システム構成図の作成、DB 選定（RDBMS vs NoSQL）、スケーリング戦略の策定、セキュリティアーキテクチャ設計（認証基盤・暗号化など）、技術スタックの選定、クラウドアーキテクチャ設計、システムアーキテクチャドキュメントの作成。

クラス設計・ドメイン設計・デザインパターン適用といったアプリケーション層の設計は `software-design` skill を参照する。技術の比較・選定は [technology-selection.md](technology-selection.md)、レビュー時は [system-design-review.md](system-design-review.md) を使う。
