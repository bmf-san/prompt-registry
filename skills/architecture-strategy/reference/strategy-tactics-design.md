# 戦略・戦術・設計の書き分け

アーキテクチャドキュメントを「戦略・戦術・設計」のどの層に書くべきか迷ったときの書き分け指針。5W1H を各層に割り当てて役割を明確にする。特に戦術（施策の大枠）が戦略や設計に埋もれやすいので、意識して切り分ける。

## 3層構造

- **戦略**: Why / What — なぜ取り組むのか、何を達成したいのか（最も抽象的）
- **戦術**: How / When / Where / Who の大枠 — どの施策で、いつ、どこに、誰が
- **設計**: How の詳細 — インターフェース・データモデル・技術選定の詳細（最も具体的）

戦略で方向性、戦術で施策の大枠、設計で実装方針を決める。策定時は3層を横断して考えるが、書く・整理するときはこの3層で分けると整理しやすい。

## 5W1H による書き分け基準

| 層 | 割り当て | 書く内容 |
|---|---|---|
| 戦略 | **Why / What** | 目的・動機・ビジネス価値 ／ 達成したいゴール・解決したい課題 |
| 戦術 | **How / When / Where / Who** | 施策の大枠 ／ タイムライン・フェーズ・優先順位 ／ 適用範囲 ／ 担当チーム・ステークホルダー |
| 設計 | **How の詳細** | 技術選定・インターフェース・データモデル ／ 非機能要件の具体値 ／ トレードオフの比較 |

## よくある混乱パターン

- **戦略に手段（How）を書いてしまう**: 「マイクロサービス化する」は手段＝戦術。戦略に書くべきは「なぜマイクロサービス化が必要か」という目的（例: チーム間の依存を減らし独立したデリバリーを可能にする）。
- **手段が前提になり目的を見失う**: 手段を念頭に方向性を考えると「なぜやるのか」が曖昧になる。手段を戦略から分離すると、戦略の抽象度と方針としての固さを保てる。

## 書く前に整理するインプット

書き分ける前に前提を揃える。曖昧なまま書くと形だけのドキュメントになる。

1. ビジネス戦略・ビジョン（ビジネス目標、事業ドライバー、ステークホルダーの要件・制約・期待）
2. 要件（機能要件・非機能要件）
3. 現状（As-Is）のアーキテクチャと課題・リスク
4. 制約条件（予算・人員・期限、組織構造・チーム体制）

規制・コンプライアンス、外部依存、過去の ADR など、状況に応じて必要なインプットは変わる。

## 判断に迷うグレーゾーン

すべてが明確に分類できるわけではない。例: 戦略の中で To-Be のコンテキストレベル構成を描くと、システム境界という戦術的要素が混じる。

**判断基準は「手段が前提になっていないか？」**。手段が前提だと目的を見失いやすい。戦略から手段を分離すれば、手段は状況で柔軟に変えつつ、目的はブレにくくできる。

## 策定例（骨子）

- **課題分析**: 機能リリースに平均4週間。主因はモジュール間の依存（他の原因にも波及）。ビジネス影響（大型案件の失注）と全社戦略「市場変化への迅速な対応」との適合を確認する。
- **戦略（Why / What）**: Why=デリバリー遅延で競争力が低下、全社戦略の実現のため最優先。What=モジュール依存を減らし独立デプロイ可能にし、リリースを平均2週間へ。
- **戦術（How / When / Where / Who）**: How=受注・在庫サービスを分離し CI/CD を構築。When=Q1 受注分離 → Q2 在庫分離 → Q3 整備と効果測定。Where=依存が最も複雑な受注・在庫領域（他は次フェーズ）。Who=各サービスチーム＋プラットフォームチーム。
- **設計**: 連携方式（初期は REST、将来は非同期）、データ分離（専用 DB ＋ 移行期間の双方向同期）、API バージョニング、非機能要件（可用性 99.9%・p95 200ms 等）、トレードオフ（同期 vs 非同期、共有 DB vs 専用 DB）。

## まとめ

- 戦略には Why・What、戦術には How・When・Where・Who の大枠、設計には How の詳細を書く。
- 迷ったら「手段が前提になっていないか？」で判断する。
- 手段を戦略から分離し、詳細を設計に委ねると、各ドキュメントが適切な抽象度で保てる。
