# コードレビュー

コードを 6 つの観点（正確性・可読性・保守性・効率性・セキュリティ・テスタビリティ）で評価し、具体的な改善案を根拠付きで提示するためのスキル。他人のコードをレビューするとき、自分の実装を提出前に点検するとき、バグの原因を切り分けるときに使う。単に「正解」を渡すのではなく、なぜそうするのかを説明して相手の実装スキル向上につなげることを重視する。

## レビューの手順

1. **文脈を把握する**: 何を実装したコードか、使用言語・フレームワーク、期待する入出力・制約条件を確認する。
2. **既存コードとの関係を掴む**: 関連する既存コードのコーディングスタイル・命名規則・パターンを確認し、レビュー対象がそれに沿っているかを見る。
3. **観点ごとに評価する**: 後述の 6 観点とチェックリストで、抜け漏れなく点検する。
4. **改善案を根拠付きで示す**: 問題点を指摘するだけで終わらせず、改善後のコードと改善理由・影響範囲をセットで提示する（フォーマットは後述）。

守ること:

- 指摘は 6 観点のどれに当たるかを明示する。
- 主観的な好みではなく、可読性・保守性など客観的な基準で語る。
- 相手が理解できる説明を添える。理由なしにコードだけを渡さない。

## レビュー観点とチェックリスト

### 1. 正確性・基本
- [ ] コードは正しく動作するか
- [ ] エッジケースに対応しているか
- [ ] エラーハンドリングは実装されているか
- [ ] 既存のコーディング規約に従っているか

### 2. 命名
- [ ] 変数名・関数名は意図を明確に表しているか
- [ ] マジックナンバーは定数化されているか
- [ ] 略語は適切に使われているか

### 3. 構造・保守性
- [ ] 関数は適切な長さか（目安: 50行以内）
- [ ] 1関数1責務の原則を守っているか
- [ ] 重複コードはないか（DRY 原則）
- [ ] ネストは深すぎないか（目安: 3段階以内）
- [ ] 変更の影響を局所化できる抽象化レベルになっているか

### 4. パフォーマンス・効率性
- [ ] 計算量は許容範囲か（O記法で評価する）
- [ ] 不要なループや処理はないか
- [ ] データベースのN+1問題はないか
- [ ] メモリリークの可能性はないか

### 5. セキュリティ
- [ ] ユーザー入力は検証・サニタイズされているか
- [ ] SQLインジェクションの可能性はないか
- [ ] XSSの可能性はないか
- [ ] 認証・認可は最小権限の原則に従って実装されているか

### 6. テスタビリティ
- [ ] 依存関係は注入可能か（モックに差し替えられるか）
- [ ] 副作用は最小化されているか
- [ ] テストしやすい構造か

### 可読性（全観点に通底）
- [ ] コメントには「なぜそうしたか」を説明しているか
- [ ] コードの意図は明確か
- [ ] 複雑なロジックには説明があるか

## 改善提案の提示方法

問題点や改善点は以下の形式で提示する。

```
【該当コード】
（問題のあるコード部分を引用）

【問題点】
何が問題か（上記6観点のどれに関わるか）

【改善案】
（改善後のコード）

【改善理由】
なぜこの修正で改善されるのか

【影響範囲】
この変更による影響（あれば）
```

## 実装時に意識する品質観点

レビューの裏返しとして、実装フェーズでは次を常に意識する。ここを押さえておくとレビューで指摘される前に品質を担保できる。

1. **可読性**: 意図が伝わる命名、なぜそうしたかを書くコメント、1関数1責務での分割。
2. **保守性**: DRY原則の遵守、変更の影響を局所化できる抽象化、変更が容易な構造。
3. **堅牢性**: エラーハンドリング、エッジケースへの対応、入力値の検証。
4. **パフォーマンス**: 計算量の考慮、不要な処理の削減、リソースの確実な管理（メモリリーク防止）。
5. **セキュリティ**: 入力値のサニタイズ、SQLインジェクション・XSS等の脆弱性防止、最小権限の原則に従った認証・認可。

実装の進め方の原則:

- **小さく始める**: 一度に大きく実装せず、小さな単位で動作確認しながら進める。
- **既存パターンに従う**: 既存のコーディングスタイル・命名規則に合わせる。
- **段階的に実装**: コア機能 → エラーハンドリング → エッジケース対応の順で進める。

コードを提示するときは「何を実装したか」「コード」「ポイント（選択したアプローチとその理由・注意点）」をセットで説明する。

## デバッグの進め方

バグやエラーの解決を支援するときの手順。

1. **問題を特定する**: エラーメッセージを分析し、再現条件を確認し、ログから問題箇所を絞り込む。
2. **原因を調査する**: 考えられる原因を複数挙げ（仮説）、各仮説の検証方法を示し、問題を小さな単位に切り分けて調査する。
3. **解決策を提案する**: 以下の形式でまとめる。

```
【問題の原因】
何が原因で問題が発生しているか

【解決策】
（修正コード）

【なぜこれで解決するか】
修正の根拠

【再発防止】
同様の問題を防ぐための方法（あれば）
```

## 守ること

- なぜそう実装／修正するのか、理由を説明せずにコードだけを渡さない。
- ユーザーが理解できる説明なしに「正解」を一方的に押し付けない。
- 言語・フレームワークのベストプラクティスを無視した実装を提案しない。
- 動作確認できない「理論的に完璧」な実装を、現実的な選択肢として押し付けない。
- アーキテクチャレベルの設計判断（技術スタック選定、システム全体の構成変更など）はこのスキルの範囲外。設計の妥当性は software-design、CTO・アーキテクト視点のレビュー観点は technical-review スキルを併用する。
