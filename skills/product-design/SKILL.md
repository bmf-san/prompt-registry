# プロダクトデザイン（UX/UI）

使いやすく・わかりやすく・魅力的なプロダクト体験を設計する。ユーザーのニーズと行動を理解し、それを直感的なインターフェースとスムーズな体験フローに落とし込む。ユーザー理解 → 情報設計 → UIデザイン → インタラクション → 仕様書の順で、前段の合意を得てから次に進む。

## いつ使うか

- 新しい機能・画面の UX/UI を設計するとき
- ユーザーフロー・情報アーキテクチャ・ワイヤーフレームを作るとき
- UIコンポーネント、レスポンシブ、インタラクション、アクセシビリティを検討するとき

判断は常に個人のビジュアルの好みではなく、ユーザーのニーズとプロダクト目的を基準にする。

## 1. ユーザー理解（デザイン着手前に必ず行う）

- **ターゲットユーザー**: 誰が使うか（年齢層・ITリテラシー・利用環境）／主要ペルソナ
- **利用シーン**: どんな状況・いつ・どこで・どのデバイスで使われるか（PC/スマホ/タブレット）
- **ユーザーのゴール**: 何を達成したいか／現在どう達成しているか／その方法の何が不便か

あわせて要件を確認する。機能要件と優先順位、非機能要件（アクセシビリティ要件＝WCAG準拠など、レスポンシブ対応の要否、ブランドガイドラインの有無）、制約条件（既存デザインシステム、使用可能なUIコンポーネント、スケジュール）。

## 2. 情報設計

### ユーザーフロー

ゴール達成までの流れを設計する。ポイント:

- ステップ数は最小限に（3〜5ステップが理想）
- 各ステップでユーザーが迷わないか
- エラーや中断時の対応は明確か
- 戻る・やり直す手段は提供されているか

各ステップは「ユーザーのアクション／システムの応答／想定される疑問・不安／それへの対処」を書き出す。

### 情報アーキテクチャ

- **コンテンツの整理**: どんな情報があるか／どうグループ化するか／どんな階層構造にするか
- **ナビゲーション設計**: グローバル（常に表示）／ローカル（特定画面内）／パンくずリスト（必要な場合）
- **検索・フィルタリング**: 検索機能の要否／フィルター・ソートの要否

### ワイヤーフレーム

- 詳細なビジュアルは含めない（グレースケール・シンプルな図形で表現）
- レイアウト・情報の優先順位・要素の配置に集中する
- 画面の状態（初期表示・入力中・エラー時など）を網羅する

## 3. UIデザイン

ワイヤーフレームの承認後に詳細化する。

- **トーン&マナー**: フレンドリー/フォーマル、モダン/クラシック、ミニマル/リッチ
- **カラースキーム**: プライマリ（ブランド）／セカンダリ／アクセント／テキスト・背景
- **タイポグラフィ**: フォントファミリー／見出し・本文サイズ／行間・字間

### UIコンポーネント

ボタン・入力フィールド・チェックボックス/ラジオ・ドロップダウン・カード/リスト・モーダル/ダイアログ・アラート/通知などを設計する。各コンポーネントは状態別に定義する。

- 通常状態 / Hover状態 / Active・Focus状態 / Disabled状態
- あわせて外観・サイズ・使用箇所を記述する

### レスポンシブデザイン

ブレークポイントの目安と各デバイスでの考慮点:

- **Mobile（〜767px）**: タッチ操作を考慮したボタンサイズ（最小44×44px）／片手操作を意識した配置／スクロール量の最小化
- **Tablet（768〜1023px）**: 横持ち・縦持ち両対応／タッチとマウス両方を想定
- **Desktop（1024px〜）**: キーボードナビゲーション対応／マウスホバー状態の表現

## 4. インタラクションデザイン

### マイクロインタラクション

細かな操作へのフィードバックを設計する。ボタンクリック時のアニメーション、フォーム入力時のバリデーション表示、ローディング状態、成功・エラーメッセージ、ページ遷移のトランジションなど。各インタラクションは「トリガー／動作／目的（ユーザーに何を伝えるか）」で書く。

### エラー状態・エッジケース

正常時以外の状態も必ず設計する。各状態で「ビジュアル（色・アイコン）／メッセージ（わかりやすい説明）／アクション（次に何をすべきか）」を定義する。

- エラー状態（入力エラー・システムエラー）
- 空状態（データがない場合）
- ローディング状態（データ取得中）
- 成功状態（処理完了）
- 権限不足状態（アクセス不可）

## 5. アクセシビリティ

後回しにしない。設計段階から次を作り込む。

- カラーコントラスト比の確保
- キーボード操作対応
- スクリーンリーダー対応

## 6. デザイン仕様書と開発者への引き継ぎ

仕様書は「概要／デザインシステム（カラーパレット・タイポグラフィ・スペーシング・グリッド）／UIコンポーネント（状態別の外観・使用例）／画面設計（レスポンシブ時の変化・インタラクション）／アクセシビリティ／アセット／実装上の注意点」で構成する。

開発者へは次を明確に伝える。

- **デザインの意図**: なぜそのデザインにしたか
- **優先順位**: どの部分が重要か
- **制約**: 守るべきデザイン上のルール
- **柔軟性**: 調整可能な部分とそうでない部分

## 守ること

- ユーザー・コンテキストの理解なしにデザイン作成を始めない
- アクセシビリティ対応を後回しにしない
- 個人のビジュアルの好みを根拠に評価しない（常にユーザーのニーズとプロダクト目的で判断する）
- ユーザーフローの合意なしに UI デザインの詳細化を進めない
- 不必要な複雑さを「リッチ」とポジティブに評価しない

## 扱う範囲・扱わない範囲

- **扱う**: ユーザーフロー設計／情報アーキテクチャ設計／ワイヤーフレーム／UIデザイン／デザインシステム構築／プロトタイプ（デザインツール上）／アクセシビリティ対応／レスポンシブデザイン／デザイン仕様書作成
- **扱わない（他領域）**: 要件定義・優先順位付け・ビジネス判断（プロダクトマネジメント）／システムアーキテクチャ設計・技術選定（アーキテクト）／フロントエンド実装・コーディング（エンジニア）。ただしフロントエンド実装の実現可能性は協議する
