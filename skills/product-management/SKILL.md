# プロダクトマネジメント

「何を作るべきか」「なぜ作るべきか」を明確にする。ビジネス価値の最大化・ユーザーニーズの理解・実現可能性の評価を通じて、適切なプロダクト判断へ導く。課題発見 → 要件定義 → 仕様策定 → バックログ管理の流れで進める。

## いつ使うか

- 新規プロダクト・機能追加の企画や要件定義をするとき
- ユーザーストーリーやプロダクト仕様書を作成するとき
- 要件の優先順位付け、スコープの線引き、KPI・成功指標の設定をするとき
- 「作るもの」だけが先行し、「誰の何の課題を解くか」が曖昧なとき

## 1. 課題発見・整理

### 課題の深掘り

本質的な課題を、次の問いで明らかにする。

1. **現状の理解**: どんな問題が起きているか／誰が困っているか／どの程度の頻度で発生しているか
2. **Why（なぜ）の追求**: なぜその問題が発生しているか／解決する必要があるのはなぜか／解決しないとどうなるか
3. **影響範囲の確認**: 誰がどう影響を受けているか／ビジネスへの影響／ユーザーへの影響

### ゴールの明確化

- **目指す状態**: 問題が解決されたらどうなるか／成功の指標は何か（KPI・メトリクス）
- **スコープの設定**: 今回取り組む範囲／取り組まない範囲（意図的に除外するもの）

## 2. 要件定義

### ユーザーストーリーの作成

```
【ユーザーストーリー】

As a [ユーザーの種類]
I want to [やりたいこと]
So that [達成したい目的]

【受け入れ基準】
- [ ] 〇〇ができること
- [ ] △△の場合、〇〇となること
- [ ] ××が表示されること

【背景・理由】
なぜこのストーリーが必要か
```

### 要件の整理

- **機能要件**: ユーザーができること／システムが提供する機能
- **非機能要件**: パフォーマンス（応答時間・処理速度）／可用性（稼働時間・障害対応）／セキュリティ（データ保護・アクセス制御）／ユーザビリティ（使いやすさ・アクセシビリティ）
- **制約条件**: 予算／スケジュール／技術的制約／法的・規制上の制約

### 優先順位付け

すべての要件に MoSCoW で優先順位を付ける。

- **Must Have（必須）**: これがないとプロダクトが成立しない
- **Should Have（重要）**: あるべきだが、なくても最低限は機能する
- **Could Have（あれば良い）**: あると価値が高まるが優先度は低い
- **Won't Have（今回は対象外）**: 将来検討するが今回は含めない

判断軸として各要件を次で評価する。

- ユーザー価値（High/Medium/Low）
- ビジネス価値（High/Medium/Low）
- 実現難易度（High/Medium/Low）
- 緊急度（Urgent/Soon/Later）

推奨: **ユーザー価値High × ビジネス価値High × 実現難易度Low** の要件から優先的に取り組む。

## 3. プロダクト仕様策定

優先順位付けした要件をもとに仕様書を作成する。

```
# プロダクト仕様書

## 1. 概要
- プロダクト名 / 目的 / ターゲットユーザー

## 2. 背景・課題
- 解決したい課題 / 現状の問題点 / なぜ今取り組むべきか

## 3. ゴール・成功指標
- 目指す状態 / KPI・メトリクス / 成功の定義

## 4. ユーザーストーリー
- 主要なユーザーストーリー（優先度順） / 受け入れ基準

## 5. 機能要件
- 必須（Must Have） / 重要（Should Have） / あれば良い（Could Have）

## 6. 非機能要件
- パフォーマンス / セキュリティ / ユーザビリティ

## 7. 制約条件
- スケジュール / 予算 / 技術的制約

## 8. スコープ外
- 今回は対象外の項目（Won't Have） / 将来的な検討事項

## 9. リスクと対応策
- 想定されるリスク / 各リスクへの対応策

## 10. 次のステップ
- デザインフェーズへの引き継ぎ / アーキテクチャ設計への引き継ぎ
```

### ステークホルダーとの合意形成

- **ユーザー・顧客**: 要件が本当にニーズに合っているか
- **ビジネス側**: ビジネス価値が十分か、ROIは妥当か
- **開発チーム**: 実現可能か、期間・コストは妥当か
- **デザイナー**: UX/UI設計に必要な情報は揃っているか

## 4. プロダクトバックログ管理

開発が始まったら継続的に管理する。

- **作成と維持**: ユーザーストーリー単位でアイテム化し、優先度・見積もり・受け入れ基準を付与する
- **優先順位の継続的な見直し**: ユーザーフィードバック・ビジネス状況の変化・技術的制約を反映する
- **リファインメント**: 不明確な要件の明確化／大きなストーリーの分割／受け入れ基準の詳細化
- **コミュニケーション**: 進捗の共有（状況報告・完了機能のデモ）／方向性の調整（フィードバック収集・スコープ変更判断・リスクの早期共有）

## 守ること

- 「なぜ作るか」を明確にせずに「何を作るか」だけを先に決めない
- データや事実なしに憶測だけで要件を定義しない
- Must Have を絞り込まずにスコープを無制限に広げない
- ユーザー価値を置き去りにしてビジネス価値だけで判断しない
- 優先順位や判断理由を共有せずにこっそり実装させない
- 状況変化を無視してスコープや優先順位を固定しない

## 扱う範囲・扱わない範囲

- **扱う**: 新規プロダクト企画／機能追加の要件定義／ユーザーストーリー作成／バックログ管理／優先順位付け／ステークホルダー調整／仕様書作成／KPI・成功指標の設定／ユーザーリサーチの計画
- **扱わない（他領域）**: UX/UI設計・画面設計（プロダクトデザイン）／技術的な設計・アーキテクチャ選定（アーキテクト）／実装・コーディング（エンジニア）
